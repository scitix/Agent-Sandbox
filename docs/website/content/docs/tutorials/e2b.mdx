# Agent Sandbox CLI Guide

Agent Sandbox is a Kubernetes platform that hands out isolated sandboxes for
agentic workloads: evaluations, rollouts, and agents that need somewhere to run
code that is not your laptop. Two tools reach it, and the split between them is
the product:

| Tool | Covers |
|---|---|
| `abx` | the platform — environments, warm pools, autoscaling, quotas, templates |
| E2B SDK | the sandboxes themselves — create, exec, files, network |

This guide is written for two readers at once: a person following it in a
shell, and a coding agent the document is handed to. Copy it whole; the only
values you have to supply are your console's address, your key, and the name of
the environment you are using. Values written in `UPPER_CASE` are placeholders.

## 1. Get an API key

Create one in the console, under **API Keys**. The plaintext is shown once at
creation; the platform keeps a copy you can retrieve from that page.

If the key is going to an unattended agent, issue it in **agent** mode — see
[section 6](#6-what-the-key-can-do).

## 2. Install `abx`

One binary, nothing behind it — no Node.js, no virtualenv.

```bash
curl -fsSL https://oss-ap-southeast.scitix.ai/scitix/packages/agentbox/cli/latest/install.sh | sh
```

The script installs the binary to `~/.local/bin/abx` (and tells you if that
directory is not on your PATH) and writes nine skills to `~/.agents/skills` —
see [section 4](#4-connect-a-coding-agent).

## 3. Point it at your deployment

```bash
abx context set YOUR_CONSOLE_NAME \
  --endpoint 'https://YOUR_CONSOLE/agentbox' \
  --api-key agbx_...

abx envs
```

That is the entire configuration: the console's address and the key.

- The **address** reaches the platform, not one cluster. `abx clusters` lists
  every cluster it has, and any command takes `--cluster <id>`; a single-cluster
  platform fills it in for you.
- The **auth header** follows from the address, so there is nothing else to
  configure.
- To use several Agent Sandbox platforms, save each as its own context and
  switch between them with `abx context use <name>`. The context is *which
  platform*; `--cluster` is *which of its clusters*, per command.

```bash
abx agent-context     # the whole CLI as JSON — hand this to an agent
abx envs YOUR_ENV pools
```

In CI or other unattended settings, `AGENTBOX_ENDPOINT` and `AGENTBOX_API_KEY`
stand in for a context.

## 4. Connect a coding agent

**Claude Code** — the plugin stores your key in the OS keychain, where the agent
never sees it:

```
/plugin marketplace add scitix/agent-sandbox
/plugin install agentbox
```

Then set the endpoint and key in the plugin's settings; a hook writes them to
`~/.config/abx/config.json` for the CLI to read.

**Codex, or anything else that runs shell** — the install in step 2 already
placed the binary on your PATH and nine skills in `~/.agents/skills`. Point your
agent at that directory and it has the platform's vocabulary: rollouts,
capacity, evaluations, Docker-in-sandbox, egress isolation, vault secrets. Give
it an **agent**-mode key ([section 6](#6-what-the-key-can-do)), not an
unrestricted one.

## 5. Run code in a sandbox

Every environment carries the documentation its template was written with,
rendered for the cluster it lives on — the E2B API URL, the data-plane domain,
and the scheme to use:

```bash
abx envs YOUR_ENV docs
```

Read it before driving an environment through E2B. It is the only place that
knows which endpoints your cluster answers on, and the failure it prevents is
the quiet one: an SDK pointed at the wrong host never connects and never says
why. The console shows the same document on the environment's page, with your
key filled in.

Sandboxes are E2B's surface, so the official SDK works unchanged — one call
before the import points it at Agent Sandbox instead of `e2b.dev`.

```bash
uv venv && source .venv/bin/activate
uv pip install e2b agent-sandbox-e2b
```

```python
import os

os.environ["E2B_API_KEY"] = "agbx_..."        # your key
os.environ["E2B_API_URL"] = "https://YOUR_GATEWAY/agent-sandbox/api/e2b"
os.environ["E2B_DOMAIN"] = "YOUR_GATEWAY/agent-sandbox/api/data"
os.environ["E2B_HTTPS"] = "true"              # "false" for a plain-http data plane

from agent_sandbox_e2b import patch_e2b       # must run BEFORE importing Sandbox
patch_e2b()

from e2b import Sandbox

sbx = Sandbox.create("YOUR_ENV", timeout=3600, secure=False)
print(sbx.commands.run("python -V").stdout)
sbx.kill()
```

`patch_e2b()` takes the same three values as arguments (`api_url=`, `domain=`,
`https=`) if you would rather not use environment variables. Each falls back to
its environment variable and then to the in-cluster defaults, which are what a
sandbox inside the cluster should use.

The first argument to `Sandbox.create()` is an **environment name**, not an
image. Prefix it with a cluster id to reach another cluster:
`Sandbox.create("other-cluster::YOUR_ENV")`.

## 6. What the key can do

An API key acts as **you** — your team, your namespace, your quota. It cannot
list or reach another user's sandboxes. Delete it in the console and it stops
working everywhere, including in any agent you handed it to.

For unattended use, issue the key in **agent** mode:

- the platform writes it makes (create an environment, scale a pool, delete
  anything) wait for your approval in the console;
- it cannot issue itself another key;
- it cannot read key material — not from `abx api-keys`, and not from a rendered
  setup document;
- sandbox operations (create, exec, files) behave exactly as in unrestricted
  mode.

Rendered documentation never carries a live key, for anyone. That is what makes
these documents safe to paste into a chat, a wiki, or an agent's context — which
is precisely what they are for.

## Sandbox parameters

Two timeout controls, which combine freely.

### Idle timeout

`timeout` is the sandbox's **idle** lifespan in seconds: with no active
gRPC/WebSocket/HTTP connection for that long after creation, the sandbox is
reclaimed.

```python
sbx = Sandbox.create("YOUR_ENV", timeout=3600, secure=False)   # 1 hour idle
```

| Value | Behaviour |
|---|---|
| `0` or omitted | never times out |
| positive integer (seconds) | idle timeout |

Extend it during a session with `set_timeout` — before a long stretch with no
traffic, not after it:

```python
sbx.set_timeout(1800)
```

### Startup timeout

How long `Sandbox.create()` waits for a Pod to become ready, default 120s. Set
it with the reserved metadata key `agentbox.scitix.ai/startup-timeout`; on
timeout the call raises instead of hanging:

```python
sbx = Sandbox.create(
    "YOUR_ENV",
    timeout=3000,
    secure=False,
    metadata={"agentbox.scitix.ai/startup-timeout": "120"},
)
```

### Custom images

Override the pool's default image with the reserved key
`agentbox.scitix.ai/image`, or the `ENV_NAME//image` shorthand:

```python
sbx = Sandbox.create(
    "YOUR_ENV",
    timeout=3000,
    secure=False,
    metadata={"agentbox.scitix.ai/image": "registry.example.com/my-env:v2"},
)

# Shorthand, with a cluster: CLUSTER_ID::ENV_NAME//IMAGE
sbx = Sandbox.create(
    "CLUSTER_ID::YOUR_ENV//registry.example.com/my-env:v2",
    timeout=3000,
    secure=False,
)
```

### Scaling group

When an environment fronts pools of several sizes, each tagged with a scaling
group such as `1c2Gi`, pin a create to one group with
`agentbox.scitix.ai/scaling-group`:

```python
sbx = Sandbox.create(
    "YOUR_ENV",
    secure=False,
    metadata={"agentbox.scitix.ai/scaling-group": "1c2Gi"},
)
```

This is a hard constraint: an environment with no pool in that group fails the
create rather than falling back. When the group has no idle Pod, the create
blocks until one arrives (up to the startup timeout), and drives autoscaling if
that group has it enabled. Omit the key to let the scheduler choose.

## FAQ

**`Sandbox.create()` hangs.**

It is waiting for a Pod to become ready — from the warm pool, or from a cold
start. Set `agentbox.scitix.ai/startup-timeout` so it fails with a reason
instead of waiting indefinitely.

**A sandbox disappeared.**

Check `timeout`. A task that goes quiet for longer than the idle timeout loses
its sandbox; call `set_timeout()` before the quiet stretch begins.

**The SDK never connects.**

Check the values from `abx envs YOUR_ENV docs` against what the SDK was pointed
at, and remember `patch_e2b()` has to run **before** `from e2b import Sandbox`. A
wrong scheme (`http` against an `https` data plane) fails the same way, and
never mentions the scheme in the error.
